# Counterbalanced PostgreSQL study: retained AMD64 block

[Run 44339321591](https://github.com/jonathanagustin/uds-takserver/actions/runs/44339321591), attempt 1, source `fa1f45c4241caadb8b8b3f18f55ce46265268340`, completed all nine AMD64 sessions in job 134924614887. The exact records from artifact 14466572019 are retained under [records/](records/). [sources.json](sources.json) binds the source, run, job, artifact ZIP, every original record and the validation code. Record bytes were not normalized.

The existing `bench.postgis_study.record_identity` and `complete` checks accept the full nine-session block. They validate native runner/source identity, pinned tester/configuration hashes, retained database identity and restarts, workload boundaries, settings and resource limits. The three validation/fixture files are byte-identical to the measured source. [report.md](report.md) is generated by the existing `report_lines` function.

Each configuration has three counterbalanced session repeats on one retained database with shared cache/data history: 50 clients, at least 300 seconds warmup, then 1200 seconds measured. PostgreSQL 18.6/PostGIS 3.6.4, durability enabled and database cgroup limits remain part of the acceptance contract. Cyclic order balances ordinal position; it does not remove all carryover effects or create independent installation replicates.

Received throughput medians range from 495.199 to 495.350 messages/s. Mean ping-pong latency medians range from 430.428 to 437.148 ms, with overlapping repeat ranges. These observations do not establish a causal tuning benefit or justify changing production settings. Ping-pong latency is a measured mean, not p95, database query latency or a delivery percentage.

The measured source predates the accepted Temurin runtime change. These results describe that exact historical application/runtime source; they do not qualify the current runtime. ARM64 failed installation before measurement, so there is no ARM block, cross-architecture comparison or ISA ranking. Its failed steps and stale debug uploader remain separate from the successful AMD64 job; stopping that uploader does not turn the overall run into a successful two-architecture study.

This supplies the AMD64 experimental block for #49 only. Keep #49 and #51 open for their remaining scope; no new default, startup-speed claim or production-capacity claim follows from these results.
